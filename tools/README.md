# tools —— 开发辅助脚本

都是**可选**的辅助工具，不参与小程序运行、不参与云函数部署。
在**项目根目录**执行即可（脚本内部用绝对路径，不依赖当前目录）：

```bash
node tools/<脚本名>.js
```

> 一次性脚本已归档到 [`_archive/`](_archive/README.md)，需要时再搬回来。

> ⚠️ **写这类测试时最容易踩的坑：不要断言 HTTP 状态码，要断言 body 里的 `code`。**
>
> `/admin-api/*` 的业务结果**不体现在 HTTP 状态码上**，两种模式还不一样：
> - **本地模式**（没填 Key）：本地服务自己处理，`code` 为 401/403/400 时会**同时**设成真 HTTP 状态码；
> - **云端模式**（填了 Key，后台接线上数据）：请求被**透传给云函数**，统一 `json(res, 200, out)` ——
>   **HTTP 恒为 200**，结果全在 `body.code` 里。
>
> 只判 `res.status === 401` 的断言，在云端模式下 100% 假失败（曾经如此：

> 判定「被拒绝」请用「HTTP 401 **或** body.code 401」，并额外确认**没有下发 token**。
> 唯一真的走 HTTP 状态码的是**路由未命中**（未知路径 → 404）。
>
> `server/public/index.html` 的 `API.req()` 也踩过同一个坑：只判 `res.status === 401` 才登出，
> 于是**云端模式下会话过期不会跳回登录页**（已修：同时判 `j.code === 401`，但排除登录接口本身）。

> 管理后台页面本身在 `server/public/index.html`，

>

> config 可能会通过接口下发给客户端，混进去等于泄露后台密码。

> 注意：导出的 `db.load()` 是**同步内存读取**（参数被忽略）；
> 真正的强制重载入口是 `db.ensure(force)`。

## 五、线上验证

### ★ `check-deployed.js` —— 「线上云函数 vs 本地代码」版本体检（只读，最该先跑）

```bash
node tools/check-deployed.js
```

**为什么需要它**：小程序前端和云函数是**两套独立发布**的东西。
前端点「上传」更新了体验版、云函数没重新部署时，云端跑的还是旧逻辑 ——
用户看到的还是旧行为，而这一点**从界面上完全看不出来**。

真实事故（2026-10-16）：用户反复反馈「回复别人的评论还是显示成单独一条」
「外面显示 2 条评论、进去一条都没有」。用本工具一测：
线上**没有** `commentTotal`、**没有** `replyToName` ——
线上云函数早于前两轮改动，**所有后端修复从未生效过**。

原理：用 `server/.cloudbase.json` 里的 API Key 通过 CloudBase HTTP API
直接调**线上已部署的**云函数（见 `server/src/cloud.js`），
对比它返回的**字段与行为**跟本地代码是否一致。判据：

| 检查项 | 本地何时开始有 | 没有说明 |
|---|---|---|
| `GET /api/posts/:id` 返回 `commentTotal` | 「两级评论」那次改动 | 早于该改动 |
| 评论里有 `replyToName` | 「回复关系」那次改动 | 更早 |
| 列表显示的评论数 == 详情实际列出条数 | 计数改为从 comments 集合推导 | 会「外面 N 条、进去 0 条」 |
| **[4] 返回值里的图片是服务端签发的签名 https** | 「私有桶签名」那次改动（`sign.js`） | 早于该改动，或 `sign.js` 没部署 → 图片全 403/空白 |
| **[5] `/admin-api/walls` / `resources` / `groups` 存在**（未登录返回 401，不是 404） | 「后台补内容侧」那次改动 | 云函数旧版 → 后台「校园墙 / 学习资源 / 拼团管理」三页为空 |

> **[5] 的一个坑**：这三个接口注册在 `scope: 'admin'` 作用域（`route-admin.js` 全部如此），
> 用 `scope: 'api'` 去调**一律返回 404「接口不存在」**，看起来和「没部署」一模一样。
> 手工探测时务必带对 scope —— 工具里已按 `admin` 调用。

> **[4] 的背景**：存储桶 ACL 是**私有**的（`tcb.qcloud.la` 不带签名一律 403，种子图也一样），
> 而**免费/试用版环境改不了存储权限**（控制台弹「请升级至付费版」）。
> 于是改由云函数用 `getTempFileURL` 把 `cloud://` / `/static/xx.jpg` 换成签名 https 下发
> （依据：官方说「云控制台和服务端始终有所有文件读写权限，配置仅对小程序端请求有效」）。
> 判定方式：递归 walk 返回值，统计 `cloud://`、`/static/`（旧）与签名 `https`（新）的条数。
> **部署前跑会报红「仍有 N 处未签名」**，这是反向对照生效、不是 bug。

退出码：`0` = 与本地一致；`1` = 线上是旧版（**需要重新部署**）；`2` = 连不上（没配 Key 等）。

> ⚠️ 它能查出「线上落后」，但**查不出「线上缺少某个本地新改动」之外的情况** ——
> 新加一项能力后，记得在 `check-deployed.js` 里加一条判据（新字段 / 新行为），
> 否则工具会一直回 ✅ 而你以为部署成功了。

### 关于种子数据的 id（会踩到的约定）

`cloudfunctions/campus/db.js` 里 id 分两种模式（见 `plainIdMode` 的注释）：

| 场景 | id 形态 | 为什么 |
|---|---|---|
| **种子导入**（`seed.js` / `seed2.js`，只由一个实例做一次） | 朴素连续：`1、2、3…` | 分片初始化靠「重复 seed 得到**相同** id → 覆盖写」保幂等；小数字便于排查，也与线上已有的种子 id 一致 |
| **运行时新写入**（用户发帖/评论/下单…） | `seq * 65536 + 本实例随机槽位` | 多实例并发不会生成同一个 id（否则互相覆盖 = 静默丢数据） |

因此**引用演示数据的测试可以直接写 `testUserId: 2` 这类小 id**（`tools/` 下有 14 个测试这么做），
但**引用运行时新建的记录必须用接口返回的 id**。反向对照已验证：把种子也改成带槽位的模式，
那 14 个测试会立刻变红。

> 它只读、不写任何数据、不打印完整 API Key。
> 部署动作本身仍需在开发者工具里做（见 `DEPLOY.md` 第 1 步）。

## 六、约定

- 临时调试脚本以 `_` 开头命名（已加入 `.gitignore` 的忽略规则），用完即删。
- 新增可复用的测试请直接放 `tools/`，并在本文件登记，方便以后查找。
- **反向对照脚本以 `rc-` 开头命名**（rc = reverse control）：把**真实代码复制到临时目录**、注入已知 bug、重跑同一套场景，确认**测试确实会变红**。只写「测试通过」不足以证明断言有效 —— 恒真的断言也会通过。跑完自动清理临时目录。
- **改完业务逻辑，除了跑回归测试，请再跑 `node tools/check-mirror.js`**：确认云函数与本地镜像两条链路都改到了（本项目硬约定，缺一侧就会「线上好了、本地后台还是旧的」或反过来）。这是唯一能自动发现「hook 被并行 Edit 覆盖」的手段。
